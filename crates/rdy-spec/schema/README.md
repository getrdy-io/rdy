# rdy/v1 JSON schemas

| File | Describes |
| --- | --- |
| `spec.v1.schema.json` | The readiness spec a vendor writes (`apiVersion: rdy/v1`, `kind: Readiness`). |
| `result.v1.schema.json` | The JSON report `rdy run` writes and Rdy Cloud ingests (`kind: Report`), plus the `Verification` and `ErrorOutput` objects printed with `--json`. |

Both are JSON Schema draft 2020-12. The design and the compatibility rules are in
`docs/plan/01-spec-format.md`.

## Where these files come from

In the real crate these files are generated by `schemars` from the Rust types in `rdy-spec`
(`cargo xtask schema`, ADR 0012). The generator does not exist yet. Until it does, these hand-written
files are the contract. When the generator lands, a CI check compares its output with the fixture set
these files accept and reject, the generated files replace these, and from then on CI fails on any
difference between the types and the committed files.

Editors can use them today, for example with yaml-language-server:

```yaml
# yaml-language-server: $schema=https://getrdy.io/schema/rdy/v1/spec.v1.schema.json
```

rdy itself never fetches a schema at run time.

## Revisions

The wire format stays `rdy/v1` while changes are additive. Each `rdy-spec` release that changes either
file adds a line here.

| v1 revision | rdy-spec | Change |
| --- | --- | --- |
| 0 | 0.1.0 | First contract: spec envelope, 17 M1 check ids, bundle shape with `redact_patterns` and `max_size`, result report with action log and redaction summary. |
