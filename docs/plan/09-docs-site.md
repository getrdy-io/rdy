# Docs site plan: docs.getrdy.io

Owner: docs-writer. Status: planning pass, revision 2 after release-engineer review (`docs/plan/reviews/09-docs-site-review-by-release-engineer.md`). No docs pages are written yet.

After reading this, you can set up the docs skeleton, list the pages that ship in M1, and see how generated pages stay in sync with the schema, the check registry and the changelog without leaking deploy secrets.

## 1. Summary

- One Astro Starlight site in `docs/`. Only `docs/src/content/docs/` is published.
- A Rust xtask writes the generated pages: spec and result references, check family pages, and (from M2) the CLI reference and changelog. CI fails when a generated page is stale.
- Check remediation text lives in the check registry. The report and the docs print the same string.
- Docs versions follow stable releases. `/` shows the newest stable tag. `/next/` shows main. Older minors are archived from release assets, one archive per stable tag, signed with the other release assets.
- Cloudflare Pages hosts the site. Build and deploy are separate jobs. Production deploys run only from `main` and stable tags, through a protected GitHub Environment. M1 has no PR previews.
- Node runs only in the docs jobs. The Rust jobs never install Node.
- The docs gates are two jobs in `ci.yml` (`docs-gen`, `docs-build`), both required through `ci-ok`. Deploys live in `docs-deploy.yml`, which is not a required check.

## 2. Where the site lives

```text
docs/
  package.json            pnpm project; packageManager; engines; exact versions; onlyBuiltDependencies
  pnpm-lock.yaml          committed; CI installs with --frozen-lockfile
  .node-version           full Node version (section 10)
  astro.config.mjs        Starlight config: title, sidebar, base path, component overrides
  src/
    content/docs/         published pages only
      index.mdx           Overview (hand-written)
      install.mdx         and the other hand-written pages
      reference/          generated: spec, result (M2: cli)
      checks/             generated family pages; index.mdx is hand-written
      changelog.md        generated (M2)
    components/
      VersionPicker.astro header override (M2, section 8)
  public/                 static files
  plan/                   design notes; not published
  adr/                    decision records; not published
```

Rules:

- Starlight publishes `src/content/docs/` and nothing else. `plan/` and `adr/` sit beside it. The published-content guard (section 10) proves they stay out of the build.
- No Tailwind in the docs. Starlight's own styles and CSS variables are enough.
- Hand-written pages use `.md`, or `.mdx` when they need a component. Generated pages are always `.md` and start with `<!-- Generated by cargo xtask docs. Do not edit. -->`.
- No `package.json` at the repo root. Node tooling stays inside `docs/`.
- `crates/xtask` sets `publish = false` and `[package.metadata.dist] dist = false`, so dist does not treat it as an app and the release plan does not list it.

## 5. Spec reference generation

**Input.** The JSON Schema files in `crates/rdy-spec/schema/`, committed to git. Rust types in `rdy-spec` produce them with schemars. The file names come from `docs/plan/01-spec-format.md`. The renderer reads the files from disk. A schema change shows up in the pull request as a JSON diff and a Markdown diff.

**Two commands.**

- `cargo xtask schema` runs schemars and writes the schema files. With `--check`, it regenerates in memory and fails if the disk copy differs.
- `cargo xtask docs` reads the schema files and the check registry (section 6), then writes the Markdown pages. With `--check`, it fails if any generated page differs from the render. M2 adds the CLI reference and changelog to this command.

**Output.** `reference/spec/index.md` (rdy/v1 spec) and `reference/result/index.md` (JSON result) in M1, plus `checks/<family>.md`. When rdy/v2 ships, its reference goes to `reference/spec/v2/`. The v1 pages stay.

**Hand-written intros (M1-085).** The prose above each reference table is in `docs/intro/` (`reference-spec.md`, `reference-result.md`). That folder sits outside `docs/src/content/docs/`, so it is not published. The renderer puts the intro after the banner. An object that more than one field names gets one section. A later row that names it links to that section, so each field appears once. The result page also has a section for each other JSON object that rdy prints: `Verification`, `ErrorOutput`, `LintReport` and `Version`.

**Renderer rules.**

- Each property gets a row: name, type, required, default, description, example. Descriptions come from doc comments through schemars, so the rule "every public item documented" carries over.
- A property with no description fails `cargo xtask docs`, and the error names the property path.
- `oneOf` or `allOf` if/then variants render one subsection per variant. Check parameters use `allOf` with if/then, so each check kind shows its own fields.
- Examples are stored as JSON in the schema. The test suite validates each check example against the schema node it sits under, and decodes it with the rdy-spec parser. The render shows each example as YAML, checks that the YAML reads back as the same value, and checks that a variant example carries the value that selects its variant (ADR 0034).
- Output is deterministic. It depends only on committed files: no timestamps, no git history, schema key order, LF line endings. Checkouts stay shallow.

**CI check.** The `docs-gen` job runs `cargo xtask schema --check` and `cargo xtask docs --check`. A stale file fails the job, and the message names the file and the command to run.

**Ownership.** The schema emitter that turns `rdy-spec` types into schema files belongs to the `rdy-spec` owner (rust-engineer). The docs-writer reads its output and does not define it.

## 6. Check catalog generation and sync

**Source of truth.** Each check has metadata in the check registry. The fields are id, family, title, what it measures, privilege needed, supported operating systems, what it reads on each OS, thresholds, remediation text and sort order. Each lives in one place (ADR 0026): `CheckMeta` holds the title and the remediation and sits in the `meta` field of the check's static `CheckInfo`. `CheckInfo` holds the id, family, what it measures (`summary`), needs and wants (the privilege), OS support and reads. `reads` is one list for every OS, so the pages list reads without an OS split until the manifest is keyed by OS. The thresholds are the typed spec parameters in `rdy-spec`. The sort order is the order of `Family::checks`. The check author fills them in. The engine (`docs/plan/02-engine-design.md` defines the trait) returns them, and `cargo xtask checks` lists them. The CLI prints `remediation` in the report, and the docs print the same string. They cannot disagree. `CheckMeta` belongs to the registry owners (rust-architect with check-author). The docs-writer reads it.

**Output.** One page per family: `checks/host.md`, `checks/network.md` and `checks/kubernetes.md` in M1. Each check gets an H2 with its id, a short field list, and a `Remediation` block that holds the registry string word for word. Checks appear in sort order.

**Release scope.** The docs for a release show only checks that exist at its tag. A check planned for M3 does not appear on the M1 site.

**Index.** `checks/index.mdx` is hand-written and lists families and links only. It names no checks, so it cannot drift.

**Sync with `docs/plan/03-check-catalog.md` (M2).** The catalog is the design record. Once a check merges, its row in 03 keeps only id, family and milestone. Thresholds and remediation live in the registry only. `cargo xtask docs-lint` checks two things:

- every registry id appears in 03, so no check ships without a design;
- every 03 row whose milestone is the milestone being shipped has a registry entry, so no designed check goes missing at release.

The xtask holds one constant, the milestone being shipped. The last PR of each milestone updates it. The sync check needs 03 to keep a table with an `id` column (backticked) and a `milestone` column. The check author must keep that format. Until M2, the family pages are reviewed against 03 by hand.

**Ids and families.** Page slugs are `host`, `network`, `kubernetes`, `cloud`, `gpu`, `data-stores` and `custom`. Id prefixes follow the crate names: `host.`, `net.`, `k8s.`, `gpu.`. Cloud ids use `aws.` for now. The corrections ask the check author to confirm the cloud prefix before GCP and Azure arrive.

**Rule for pull requests.** A check ships with its registry entry, its remediation text, and its family page. `cargo xtask docs --check` fails until all three exist.

## 7. Changelog and CLI reference (M2)

**Changelog.** `CHANGELOG.md` at the repo root uses Keep a Changelog format, with one H2 per version. The schema-change line for each version is written into `CHANGELOG.md` at release time by a step in the release runbook. That step reads the committed schema files and diffs them against the previous stable tag. The renderer then reads only committed files, so its output is deterministic and shallow checkouts are enough.

**CLI reference.** The xtask walks the clap command tree from `rdy-cli`. It writes one H2 per command, a usage line and a flags table. To make the tree importable, `rdy-cli` has a library target named `rdy_cli` that exposes `command()`. The binary stays a thin wrapper. The library name differs from the binary's package name so that `cargo doc` does not produce colliding output.

## 8. Versioning

**Rules.**

1. One docs version per stable minor. Pre-releases (for example `0.1.0-alpha.3`) create no docs version and are not hosted separately. Before the first stable tag, `/` and `/next/` both show main, and `/` carries the banner "Pre-release. Some pages may change before the stable release."
2. `/` shows the newest stable tag. `/next/` shows main with the banner "Unreleased. This may not match any release."
3. `/v/0.N/` is an archive of minor 0.N. It is built from the newest stable tag of that minor.
4. Archives are snapshots. Docs for an old minor are not patched. If an old minor needs a fix, rebuild its archive from its tag.
5. `latest` is an alias. `/latest/*` redirects with a 302 to `/*`, so links that include `latest` keep working. Archive pages set a canonical link to the same page under `/`.
6. Keep every archive on the site until 1.0. Then decide again. Section 9 lists the Pages limits that would force a change.

**Mechanics (M2).**

- A custom `docs-archive` job runs in the dist release workflow, from a reusable workflow named in `dist-workspace.toml`. `release.yml` stays generated by dist and is never hand-edited. The job runs on each stable tag. It checks out that tag, runs `pnpm install --frozen-lockfile` and `pnpm build` with `DOCS_BASE=/v/0.N`, packs `dist/` as `rdy-docs-<tag>.tar.zst`, and attaches it to that tag's release.
- The job runs before `sign-release`, so the archive is checksummed and signed with the other release assets. Immutable releases stay possible.
- Each archive builds from the lockfile of its own tag. The release asset is the frozen copy, so an old archive does not depend on today's dependency versions.
- The deploy workflow (section 9) builds the root from the newest stable tag, builds `/next/` from main, and unpacks the newest-tag archive of each older minor under `/v/0.N/`. It writes `versions.json` at the site root:

```json
[
  { "label": "0.2.0", "version": "0.2.0", "path": "/" },
  { "label": "Unreleased (main)", "version": "main", "path": "/next/" },
  { "label": "0.1", "version": "0.1.3", "path": "/v/0.1/" }
]
```

**Version switching.** Starlight has no version switcher. The header override (`SiteTitle` is the override point Starlight documents; confirm it in the scaffold) renders a `<select>`. The select reads `/versions.json` at runtime, so an archived page shows today's list, not the list from the day it was built. Choosing a version opens the same path in that version. If the path does not exist there, the select opens that version's root.

**Search.** Starlight's default search (Pagefind) builds per version, so each archive searches only itself.

**Spec versions are separate.** `rdy/v1` appears in every docs version that supports it. Each docs version names the spec versions it covers.

## 9. Hosting and deploys

**Account and project.** A Cloudflare Pages project `rdy-docs` on a Cloudflare account used only for docs, so a token scoped to that account cannot reach other products. Custom domain `docs.getrdy.io`. Production branch `main`.

**Build and deploy are two jobs.**

- The `docs-build` job in `ci.yml` runs on every pull request. It has no secrets and read-only permissions. It uploads `docs/dist` as a workflow artifact.
- `docs-deploy.yml` runs on push to `main` and on stable tags only. Its `build` job has no secrets. Its `deploy` job runs in the GitHub Environment `docs-production`.
- `docs-production` has deployment rules that allow only `main` and `v*` tags. A pull request run cannot enter the environment, so it cannot read `CLOUDFLARE_API_TOKEN`. The environment secret is a token for the docs account only.
- The deploy job uses a wrangler version pinned in the workflow file. It does not install wrangler from the tree or the lockfile.
- Refs and PR numbers reach shell commands only through `env:`, never by interpolating titles or branch names.
- `concurrency: docs-production` with `cancel-in-progress: false`, so two merges cannot race.
- Deploys use `--branch=main`, which makes them production deployments.

**What M1 does not do.** No PR previews. A same-repo PR cannot deploy in M1, which removes the path from a PR to the production token.

**M2 previews.** A separate workflow with its own environment `docs-preview`, a token for a separate Cloudflare account, and a project `rdy-docs-preview`. Same-repo PRs only. Dependabot and fork PRs are skipped. Preview URLs follow `pr-<n>`. Previews set `<meta name="robots" content="noindex">` through `DOCS_PREVIEW=1`.

**Limits to confirm in the M2 spike.**

- File count per deployment. The documented limit was 20,000 files at the time of writing. Archives and Pagefind chunks add up.
- The 25 MiB per-file cap.
- Whether direct-upload deployments count against the monthly build cap that applies to Git-integration builds.

**Rollback.** Promote an earlier deployment in the Pages dashboard, or rerun the deploy from the earlier stable tag. Confirm the steps in M2.

**Analytics.** None on the docs in M1. Security reviewers read these pages, and the privacy story is simpler without a tracker. The founder can add Plausible in M3.

## 10. Node toolchain outside the Rust path

**Pinning.**

- `docs/.node-version` holds a full version, for example `24.11.0`, set to the current Node LTS at scaffold time.
- `docs/package.json` holds `"packageManager": "pnpm@<exact version>"` for local developers who use corepack. CI does not depend on corepack, because newer Node releases no longer bundle it.
- CI installs pnpm with `pnpm/action-setup`, pinned to a full commit SHA. It reads `packageManager`.
- pnpm 10 or newer. Dependency install scripts are off by default. `onlyBuiltDependencies` lists the packages that need scripts. The first install decides the list; expect esbuild, sharp and workerd, and confirm during the scaffold.
- `minimumReleaseAge` is set to about seven days (10080 minutes), so a freshly published package does not enter the lockfile on the day it appears. Confirm that the pinned pnpm version supports the setting.
- `actions/setup-node` runs after pnpm is installed, with `cache: pnpm`.
- Astro, `@astrojs/starlight` and `starlight-links-validator` use exact versions, not ranges.
- `docs/pnpm-lock.yaml` is committed. CI installs with `--frozen-lockfile`.
- A Dependabot entry for the npm ecosystem at `/docs` is added to the release engineer's repo settings ticket.
- `pnpm audit --prod` runs in `audit.yml`, not in a required job.

**Keeping Rust clean.**

- `rust-toolchain.toml` pins Rust only.
- The repo root has no `package.json`, no pnpm files and no `node_modules`.
- The Cargo workspace lists its members under `crates/` by name. `docs/` is not a member.
- `.gitignore` covers `docs/node_modules/`, `docs/dist/` and `docs/.astro/`.
- `ci.yml` has two docs jobs. `docs-gen` runs the xtask checks on Linux with its own rust-cache key. It never runs `setup-node`. `docs-build` runs pnpm only.
- `docs-gen` builds `rdy` for the glibc host target to run `docs-test` (M2). Its cache is separate from the musl test legs.

**CI gates for the docs.** `docs-gen` and `docs-build` are listed in `ci-ok`'s `needs`. Nothing else is a required check.

| Gate | Job | Required | Fails when |
| --- | --- | --- | --- |
| `cargo xtask schema --check` | docs-gen | yes, via `ci-ok` | The committed schema differs from the `rdy-spec` types |
| `cargo xtask docs --check` | docs-gen | yes | A generated page differs from the render |
| `cargo xtask docs-lint` | docs-gen | yes | An em dash or en dash appears in docs; a banned token hash matches any tracked text file; a remediation is empty |
| `cargo xtask docs-test` | docs-gen (M2) | yes | A tested block fails or exits outside its declared codes |
| `pnpm install --frozen-lockfile` | docs-build | yes | The lockfile is out of sync with `package.json` |
| `astro check` and `pnpm build` | docs-build | yes | An Astro or TypeScript error |
| Internal link check (`starlight-links-validator`, pinned) | docs-build | yes | An internal link or anchor is missing |
| Published-content guard | docs-build | yes | Anything from `plan/` or `adr/` appears in `dist/` |
| External link check | `audit.yml`, weekly | no | An external link returns an error |
| `pnpm audit --prod` | `audit.yml` | no | A known advisory on a production dependency |
| Production deploy | `docs-deploy.yml` | no | The upload fails; the workflow shows the reason |
| PR preview deploy (M2) | `docs-preview.yml` | no | The upload fails |

## 11. Writing style guide

The house rules apply to every page. These ten rules are the docs version.

1. **Open with what the reader can do.** The first sentence after the title says what the reader will be able to do.
2. **Use short sentences.** Aim for twenty words or fewer. One idea per paragraph.
3. **Write to "you."** Say "you run" and "rdy writes." Write `rdy` in lowercase for the command and "Rdy" for the product.
4. **Use the present tense and the active voice.** "rdy writes the report," not "the report is written."
5. **No em dashes and no en dashes.** Use a full stop, a comma or a colon. `cargo xtask docs-lint` fails on either character.
6. **Use plain words.** Avoid corporate words such as "leverage," "empower," "seamless," "robust," "solution," "journey" and "unlock." `docs-lint` also checks tracked text files for banned tokens. The banned list is stored as SHA-256 hashes of lowercase tokens in the xtask. The banned words are never written in plain text anywhere in the repo, so the check cannot leak the list it enforces.
7. **Test every command you show.** From M2, a command in a fenced block either runs in `docs-test` or it is marked as pending with the ticket that owns it. Until then, the first-run commands are integration test cases. Show real output, with synthetic names only.
8. **Give every failure a fix.** When a page names a failure, it names the remediation next to it. Copy the remediation text from the registry, not from memory.
9. **Name what is not built yet.** Write "Ships in M3," not "coming soon." Readers can plan around a milestone.
10. **Link, do not repeat.** Each fact has one home. Exit codes live on one page. Field lists come from the generated reference. Never edit a generated page; fix the generator or the source.

Examples in every doc use reserved names: `acme-platform`, `registry.acme.test`, `license.acme.test`. Never use a real company, a real hostname or a real key.

## 12. Install and first-run outline

### Install page (M1)

1. **What you get.** One binary, `rdy`. It has no runtime and no daemon. It runs as the user who starts it. Checks that need more access say so in the report.
2. **Install on Linux or macOS.** The one-line command below.
3. **Confirm the install.** `rdy version`.
4. **Install by hand (air-gapped).** Download the archive, check its checksum, unpack it. Commands depend on release engineering (`06`).
5. **Verify the signature.** The `cosign` command depends on `06`.
6. **Windows.** A zip, as `06` defines it. winget comes later.
7. **Platforms.** A table of targets. A target appears only when the release verify job passes on it.
8. **Uninstall.** Depends on `06`.

### First-run page (M1)

1. **Before you start.** `rdy version`.
2. **Verify the example spec.** The example is signed with the demo key in `examples/keys/`. Flag names depend on `01` and `07`.
3. **Run it.** `rdy run` on the example spec.
4. **Read the last line.** READY exits 0. Warnings only exit 1. Blockers exit 2. Link to Exit codes.
5. **Save the JSON.** `--json` writes the result to stdout.
6. **Open the HTML report.** The flag depends on `07`. The report page itself ships in M2.
7. **Fix and rerun.** The same command, after a fix.

The M1 example spec uses host, network and Kubernetes checks only, and reserved hostnames. A CI runner is not a customer's machine, so the integration tests check the shape of the output and the exit code, not whether the example says READY.

## Decisions needing an ADR

1. **Docs versioning mechanism.** Options: (a) in-house archives stored as release assets, one per stable tag, with a header select (chosen here, because it adds no third-party code to the release path); (b) the community Starlight versions plugin, which was not checked in this pass. Conservative choice: (a). Record the ADR before the M2 versioning tickets.
2. **Deploy path to Cloudflare Pages.** Options: (a) GitHub Actions builds, uploads an artifact, and a separate deploy job runs in a protected environment (chosen: one pinned build, and the token lives only in that environment); (b) the Cloudflare Git integration, which builds on Cloudflare's image. Conservative choice: (a). The founder creates the token and the environment. Record the ADR before the M1 production deploy ticket.
3. **Serving `getrdy.io/install`.** Options: (a) a Worker route that serves `install.sh` (owned by `06`); (b) the marketing build copies `install.sh` into its output at each release. Both avoid a redirect. Owners: release engineer and founder. Record the ADR before the install page ticket.
4. **Signing key for the example specs.** Options: (a) a public demo key committed in `examples/keys/`, with the private half only in a CI secret, which signs the examples on each release; (b) unsigned examples that need `--allow-unsigned`, which teaches customers to use the escape hatch; (c) a private key committed to the repo, which lets anyone sign a spec that looks vendor-signed. Conservative choice: (a). Owners: security reviewer and release engineer.
5. **Publication of `docs/plan/` business content.** Founder decision, not an agent decision. Until the founder decides, the docs-writer agent adds no business content to any file in `docs/plan/`, and no file in the repo names a competitor.

Closed: install.sh testing. The shipped script gets no test-only base URL variable. Tests use a stub `curl` on `PATH` and a local file server, and a post-release verify job runs against the real release. Agreed with release engineering.
