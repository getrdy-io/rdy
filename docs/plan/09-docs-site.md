# Docs site plan: docs.getrdy.io

Owner: docs-writer. Status: planning pass. No docs pages are written yet.

After reading this, you can set up the docs skeleton, list the pages that ship in M1, and see how generated pages stay in sync with the schema, the check registry and the changelog.

## 1. Summary

- One Astro Starlight site in `docs/`. Only `docs/src/content/docs/` is published.
- A Rust xtask writes the generated pages: the spec and result references, the CLI reference, the check family pages and the changelog. CI fails when a generated page is stale.
- Check remediation text lives in the check registry. The report and the docs print the same string.
- Docs versions follow minor releases. The root shows the newest tag. `/next/` shows main. Older minors are archived from release assets.
- Cloudflare Pages hosts the site. GitHub Actions builds it. Each pull request gets a preview URL.
- Node runs only in the docs job and the release archive job. The Rust jobs never install Node.
- Every command in the install and first-run guides runs in CI.

## 2. Where the site lives

```text

  pnpm-lock.yaml          committed; CI installs with --frozen-lockfile
  .node-version           pinned Node major version
  astro.config.mjs        Starlight config: title, sidebar, base path, component overrides
  src/
    content/docs/         published pages only
      index.mdx           Overview (hand-written)
      install.mdx         and the other hand-written pages
      reference/          generated: spec, result, cli
      checks/             generated family pages; index.mdx is hand-written
      changelog.md        generated
    components/
      VersionPicker.astro header override (section 8)
  public/                 static files
  plan/                   design notes; not published
  adr/                    decision records; not published
```

Rules:

- Starlight publishes `src/content/docs/` and nothing else. `plan/` and `adr/` sit beside it. Section 10 has the CI guard that proves they stay out of the build.
- No Tailwind in the docs. Starlight's own styles and CSS variables are enough.
- Hand-written pages use `.md`, or `.mdx` when they need a component. Generated pages are always `.md` and start with `<!-- Generated by cargo xtask docs. Do not edit. -->`.
- No `package.json` at the repo root. Node tooling stays inside `docs/`.

## 5. Spec reference generation

**Input.** The JSON Schema files in `crates/rdy-spec/schema/`, committed to git. Rust types in `rdy-spec` produce them with schemars. The file names come from `docs/plan/01-spec-format.md`. The generator reads the files from disk, so a schema change shows up in the pull request as a JSON diff and a Markdown diff.

**Two commands.**

- `cargo xtask schema` runs schemars and writes the schema files. With `--check`, it regenerates in memory and fails if the disk copy differs.
- `cargo xtask docs` reads the schema files, the check registry (section 6) and `CHANGELOG.md`, then writes the Markdown pages. With `--check`, it fails if any generated page differs from the render.

**Output.** `reference/spec/index.md` (rdy/v1 spec), `reference/result/index.md` (JSON result), `reference/cli/index.md`, `checks/<family>.md` and `changelog.md`. When rdy/v2 ships, its reference goes to `reference/spec/v2/`. The v1 pages stay.

**Renderer rules.**

- Each property gets a row: name, type, required, default, description, example. Descriptions come from doc comments through schemars, so the rule "every public item documented" carries over.
- A property with no description fails `cargo xtask docs`, and the error names the property path.
- `oneOf` renders one subsection per variant. Check parameters use this, so each check kind shows its own fields.
- Examples are stored as JSON in the schema. The renderer validates each example against its schema, then shows it as YAML.
- Output is deterministic: no timestamps, schema key order, LF line endings.

**CI check.** The rust job runs `cargo xtask schema --check` and `cargo xtask docs --check`. A stale file fails the job. The message names the file and the command to run.

## 6. Check catalog generation and sync

**Source of truth.** Each check has metadata in the check registry as a Rust `CheckMeta` value. The fields are id, family, title, what it measures, privilege needed, supported operating systems, what it reads on each OS, thresholds, remediation text and sort order. The check author fills these fields. The engine (`docs/plan/02-engine-design.md` defines the trait) returns them. The CLI prints `remediation` in the report, and the docs print the same string. They cannot disagree.

**Output.** One page per family: `checks/host.md`, `checks/network.md` and `checks/kubernetes.md` in M1. Each check gets an H2 with its id, a short field list, and a `Remediation` block that holds the registry string word for word. Checks appear in sort order.

**Release scope.** The release docs show only checks that exist at the release tag. A check that is planned for M3 does not appear on the M1 site.

**Index.** `checks/index.mdx` is hand-written and lists families and links only. It names no checks, so it cannot drift.

**Sync with `docs/plan/03-check-catalog.md`.** The catalog is the design record. Once a check merges, its row in 03 keeps only id, family and milestone. Thresholds and remediation live in the registry only. `cargo xtask docs-lint` checks two things:

- every registry id appears in 03, so no check ships without a design;
- every 03 row whose milestone is the milestone being shipped has a registry entry, so no designed check goes missing at release.

The xtask holds one constant, the milestone being shipped. The last PR of each milestone updates it. The check needs 03 to keep a table with an `id` column (backticked) and a `milestone` column. The check author must keep that format.

**Ids and families.** Page slugs are `host`, `network`, `kubernetes`, `cloud`, `gpu`, `data-stores` and `custom`. Id prefixes follow the crate names: `host.`, `net.`, `k8s.`, `gpu.`. Cloud ids use `aws.` for now. The corrections list asks the check author to confirm the cloud prefix before GCP and Azure arrive.

**Rule for pull requests.** A check ships with its registry entry, its remediation text, and its family page. `cargo xtask docs --check` fails until all three exist.

## 7. Changelog and CLI reference

**Changelog.** `CHANGELOG.md` at the repo root uses Keep a Changelog format with one H2 per version. The renderer copies each version to `changelog.md` and adds one line per version that lists the schema files that changed since the previous tag, found with `git diff`. Readers can see at once whether a spec or result field changed.

**CLI reference.** The xtask walks the clap command tree from `rdy-cli`. It writes one H2 per command, a usage line and a flags table. To make the tree importable, `rdy-cli` exposes a `command()` function from a library target. The binary stays a thin wrapper.

## 8. Versioning

**Rules.**

1. One docs version per minor release. Pre-releases of a minor (for example `0.1.0-alpha.3`) do not create a version. The weekly M1 builds are alpha pre-releases of 0.1. This depends on `06-release-and-distribution.md` defining the version policy that way (see corrections).
2. `/` shows the newest tag. While that tag is a pre-release, the page shows a banner: "Pre-release. Some pages may change before the stable release."
3. `/next/` shows the main branch with the banner "Unreleased." Until the first tag exists, `/` shows main.
4. `/v/0.N/` is an archive of minor 0.N, built from the last tag of that minor. The archive is created when the first tag of the next minor ships.
5. Archives are snapshots. The docs for an old minor are not patched. If an old minor needs a fix, rebuild its archive from its tag.
6. `latest` is an alias. `/latest/*` redirects with a 302 to `/*`, so links that include `latest` keep working. Archive pages set a canonical link to the same page under `/`.
7. Keep every archive on the site until 1.0. Then decide again. Pages limits the number of files in one deployment. Check the current limit before M2. If it becomes the constraint, move the oldest archives to one tarball per minor, with a page that links to it.

**Mechanics.**

- A `docs-archive` job in `release.yml` runs on the first tag of a new minor. It checks out the previous minor's last tag, runs `pnpm install --frozen-lockfile` and `pnpm build` with `DOCS_BASE=/v/0.N`, packs `dist/` as `rdy-docs-0.N.tar.zst`, and attaches the archive and its `.sha256` to the new release.
- Each archive builds from the lockfile of its own tag. The release asset is the frozen copy, so an old archive does not depend on today's dependency versions.
- The production deploy (section 9) downloads each archive asset, unpacks it under `/v/0.N/`, and writes `versions.json` at the site root:

```json
[
  { "label": "0.1.0-alpha.3", "version": "0.1.0-alpha.3", "path": "/" },
  { "label": "Unreleased (main)", "version": "main", "path": "/next/" },
  { "label": "0.1", "version": "0.1.2", "path": "/v/0.1/" }
]
```

**Version switching.** Starlight has no version switcher. The header override (`SiteTitle` is the override point Starlight documents; confirm in the scaffold ticket) renders a `<select>`. The select reads `/versions.json` at runtime, so an archived page shows today's list, not the list from the day it was built. Choosing a version opens the same path in that version. If the path does not exist there, the select opens that version's root.

**Search.** Starlight's default search (Pagefind) builds per version, so each archive searches only itself.

**Spec versions are separate.** `rdy/v1` appears in every docs version that supports it. Each docs version names the spec versions it covers.

## 9. Hosting and PR previews

- Cloudflare Pages project `rdy-docs`, custom domain `docs.getrdy.io`, production branch `main`.
- GitHub Actions builds the site. It does not use Cloudflare's build system, so the Node version and the pnpm version come from this repo. Deploys run `wrangler pages deploy`, with wrangler pinned as a devDependency in `docs/`.
- Secrets: `CLOUDFLARE_API_TOKEN` (Pages edit on one account) and `CLOUDFLARE_ACCOUNT_ID`. The founder creates the token. The agent does not hold it.
- **Production** runs on each push to main and on each release tag. It assembles the tree from section 8 and deploys it with `--branch=main`.
- **Preview** runs on each pull request from a branch in this repo. It deploys with `--branch=pr-<n>`, so the URL is `https://pr-<n>.rdy-docs.pages.dev`. The job comments that URL on the PR and edits the same comment on each push. Confirm the branch alias shape during the M1 spike.
- **Fork pull requests** build and run the tests. They do not deploy, because they have no secrets. The job summary says that previews are off for forks.
- Previews set `<meta name="robots" content="noindex">` through the environment variable `DOCS_PREVIEW=1`.
- **Rollback.** Promote an earlier deployment in the Pages dashboard, or rerun the production deploy from the tag. Confirm the exact steps in M2.
- **Analytics.** None on the docs in M1. Security reviewers read these pages, and the privacy story is simpler without a tracker. The founder can add Plausible in M3.

## 10. Node toolchain outside the Rust path

**Pinning.**

- `docs/.node-version` holds the Node LTS major that is current at scaffold time. `actions/setup-node` reads it.
- `docs/package.json` holds `"packageManager": "pnpm@<exact version>"`, which corepack uses, and `"engines": { "node": ">=<major>" }`.
- Astro, `@astrojs/starlight` and wrangler use exact versions, not ranges.
- `docs/pnpm-lock.yaml` is committed. `pnpm install --frozen-lockfile` fails when `package.json` and the lockfile disagree.
- A Dependabot entry for the npm ecosystem in `docs/` runs weekly and groups updates. The release engineer owns the Dependabot file. The docs need one entry in it.
- `pnpm audit --prod` runs in the docs job. It is informational until M2, then blocks on high severity.

**Keeping Rust clean.**

- `rust-toolchain.toml` pins Rust only.
- The repo root has no `package.json`, no pnpm files and no `node_modules`.
- The Cargo workspace lists its members under `crates/` by name. `docs/` is not a member.
- `.gitignore` covers `docs/node_modules/`, `docs/dist/` and `docs/.astro/`.
- `ci.yml` has two job groups. The `rust` jobs never run `setup-node`. They run the docs checks through `cargo xtask`, which needs no Node. The `docs` job runs pnpm only.
- `docs-test` runs on Linux only, because the install commands are POSIX shell.

**CI gates for the docs.**

| Gate | Job | Fails when |
| --- | --- | --- |
| `cargo xtask schema --check` | rust | The committed schema differs from the `rdy-spec` types |
| `cargo xtask docs --check` | rust | A generated page differs from the render |
| `cargo xtask docs-lint` | rust | An em dash, an en dash or a banned word appears in docs; 03 and the registry disagree; a remediation is empty |
| `cargo xtask docs-test` | rust (Linux) | A tested block fails or exits outside its declared codes |
| `pnpm install --frozen-lockfile` | docs | The lockfile is out of sync |
| `pnpm build` and `astro check` | docs | An Astro or TypeScript error |
| Link check | docs | An internal link or anchor is missing |
| Published-content guard | docs | Anything from `plan/` or `adr/` appears in `dist/` |
| Preview deploy | docs (same-repo PRs) | The upload fails; the job fails and comments the reason |

## 11. Writing style guide

The house rules apply to every page. These ten rules are the docs version.

1. **Open with what the reader can do.** The first sentence after the title says what the reader will be able to do.
2. **Use short sentences.** Aim for twenty words or fewer. One idea per paragraph.
3. **Write to "you."** Say "you run" and "rdy writes." Write `rdy` in lowercase for the command and "Rdy" for the product.
4. **Use the present tense and the active voice.** "rdy writes the report," not "the report is written."
5. **No em dashes and no en dashes.** Use a full stop, a comma or a colon. `cargo xtask docs-lint` fails on either character.
6. **Use plain words.** Avoid corporate words such as "leverage," "empower," "seamless," "robust," "solution," "journey" and "unlock." The banned list lives in the xtask. The old working name is on no list in this repo.
7. **Test every command you show.** A command in a fenced block either runs in `docs-test` or it is marked as pending with the ticket that owns it. Show real output, with synthetic names only.
8. **Give every failure a fix.** When the page names a failure, it names the remediation next to it. Copy the remediation text from the registry, not from memory.
9. **Name what is not built yet.** Write "Ships in M3," not "coming soon." Readers can plan around a milestone.
10. **Link, do not repeat.** Each fact has one home. Exit codes live on one page. Field lists come from the generated reference. Never edit a generated page; fix the generator or the source.

Examples in every doc use reserved names: `acme-platform`, `registry.acme.test`, `license.acme.test`. Never use a real company, a real hostname or a real key.

## 12. Install and first-run outline

### Install page

1. **What you get.** One binary, `rdy`. It has no runtime and no daemon. It runs as the user who starts it. Checks that need more access say so in the report.
2. **Install on Linux or macOS.** The one-line command below.
3. **Confirm the install.** `rdy version`.
4. **Install by hand (air-gapped).** Download the archive, check its checksum, unpack it. Commands depend on `06`.
5. **Verify the signature.** The `cosign` command depends on `06`.
6. **Windows.** Depends on `06`. winget comes later.
7. **Platforms.** A table of targets. A target appears only when the release CI passes on it.
8. **Uninstall.** Depends on `06`.

### First-run page

1. **Before you start.** `rdy version`.
2. **Verify the example spec.** The example is signed with the demo key in `examples/keys/`. Flag names depend on `01` and `07`.
3. **Run it.** `rdy run` on the example spec.
4. **Read the last line.** READY exits 0. Warnings only exit 1. Blockers exit 2. Link to Exit codes.
5. **Save the JSON.** `--json` writes the result to stdout.
6. **Open the HTML report.** The flag depends on `07`.
7. **Fix and rerun.** The same command, after a fix.

The M1 example spec uses host, network and Kubernetes checks only, and reserved hostnames. A CI runner is not a customer's machine, so `docs-test` checks the shape of the output and the exit code, not whether the example says READY.

## Decisions needing an ADR

1. **Docs versioning mechanism.** Options: (a) in-house archives stored as release assets, with a header select (chosen here, because it adds no third-party code to the release path); (b) the community Starlight versions plugin, which was not checked in this pass. Conservative choice: (a). Record the ADR before the M2 versioning tickets.
2. **Deploy path to Cloudflare Pages.** Options: (a) GitHub Actions builds and uploads with wrangler (chosen: one pinned build, and the token lives only in Actions secrets); (b) the Cloudflare Git integration, which builds on Cloudflare's image. Conservative choice: (a). The founder creates the token. Record the ADR before the first deploy ticket.
3. **How install.sh is tested in CI.** Options: (a) no test-only environment variable in the shipped script. Test it with a mock `curl` and a local HTTP server in the release harness, plus a post-release smoke test on a fresh container (chosen as conservative); (b) an override variable that points install.sh at another base URL. Option (b) makes testing easier but adds a knob to a `curl | sh` script. Owner: release engineer, with the security reviewer approving.
4. **Signing key for the example specs.** Options: (a) a public demo key committed in `examples/keys/`, with the private half only in a CI secret, which signs the examples on each release; (b) unsigned examples that need `--allow-unsigned`, which teaches customers to use the escape hatch; (c) a private key committed to the repo, which lets anyone sign a spec that looks vendor-signed. Conservative choice: (a). Owners: security reviewer and release engineer.
5. **Publication of `docs/plan/` business content.** Founder decision, not an agent decision. Until the founder decides, the docs-writer agent adds no business content to any file in `docs/plan/`.
