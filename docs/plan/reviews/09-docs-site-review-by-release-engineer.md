# Review of 09-docs-site.md by release-engineer

Reviewer: release-engineer. Date: 2026-10-27. Reviewed cold: `docs/plan/09-docs-site.md` (7,176 words, 31 M1 tickets, 85 hours). I checked it against `06-release-and-distribution.md` (my own plan). I did not edit 09.

Mechanical checks: no em dashes and no en dashes found. I did not look for the old working name by guessing it; the file only mentions it by that phrase. All 31 M1 tickets (and the later ones) are one to four hours. Most exit tests are observable. Findings follow, ranked.

## Must fix

1. **Section 9, Cloudflare secrets and PR previews: a PR can take over production.**
   - Problem. The preview job holds `CLOUDFLARE_API_TOKEN` and runs for same-repo PRs. A same-repo PR can edit the workflow itself, or the `docs/` lockfile and scripts, then read the token. The writers here are the founder and an AI agent, so this is a real path. Cloudflare Pages tokens are scoped to an account, not to one project, so the same token can deploy `--branch=main` to `docs.getrdy.io`. The job also runs `pnpm install` and a wrangler taken from the PR tree, so PR-controlled code runs next to the secret.
   - Fix.
     - Split build from deploy. The build job has no secrets and uploads `dist/` as an artifact.
     - The deploy job downloads the artifact and runs a wrangler pinned in the workflow (not from the PR's lockfile).
     - Use GitHub Environments. `docs-production` holds the production token and allows only `main` and `v*` tags. `docs-preview` holds a different token for a different Pages project (`rdy-docs-preview`), ideally in a separate Cloudflare account.
     - Skip deploys when the actor is Dependabot or the head repo is not this repo.
     - Pass the PR number through `env:`, never PR titles or branch names, into `--branch` and `--commit-message`.
     - Simplest conservative option: no PR previews in M1. Upload the built site as a workflow artifact and add previews in M2 once the split exists.
   - Same flaw in my own 06 (install script served by a Pages token "scoped to that one project"). I am fixing 06 to match.

2. **Sections 9 and 10, CI integration: nothing ties the docs gates to `ci-ok`, and the job placement collides with 06.**
   - Problem. 06 makes `ci-ok` the only required check. 09 says "rust jobs" and "docs job" without names, so the new gates would be advisory or would rename required checks. xtask checks need a full build (xtask depends on `rdy-cli` and the engine registry) on the Linux glibc host target, which our musl test legs do not cache. 09 also does not say which file holds the production deploy.
   - Fix.
     - ci.yml gets two jobs: `docs-gen` (Linux only: `cargo xtask schema --check`, `docs --check`, `docs-lint`, then `cargo build -p rdy` and `docs-test`) and `docs-build` (pnpm: frozen install, `astro check`, build, internal link check, published-content guard). Both are in `ci-ok`'s `needs`. Give `docs-gen` its own rust-cache key.
     - The deploy jobs live in a new `docs-deploy.yml` and are not required checks, so a Cloudflare outage cannot block merges.
     - `docs-deploy.yml` goes into the CLAUDE.md workflow list.
     - Dependabot: add an `npm` entry for `/docs`. I will add this to my "Repo settings, rulesets and Dependabot" ticket.

3. **Section 8 and the tickets, `docs-archive` job in `release.yml`: breaks the generated-file rule and mutates another release.**
   - Problem. `release.yml` is generated by `dist` and `dist generate --check` fails CI on any hand edit. A custom job must be a reusable workflow named in `dist-workspace.toml`. Also, 09 attaches the archive of the previous minor to the new minor's release, and runs only on the first tag of a minor. That makes a release carry an asset built from different source, and it conflicts with signing: `sign-release` signs "every asset", and docs-archive timing decides whether the archive is signed or not. It also rules out immutable releases.
   - Fix. Build one archive per tag, from that tag, and attach it to that tag's release as `rdy-docs-<tag>.tar.zst`. Add it as a dist custom job (`./docs-archive`) that runs before `sign-release` so the archive is checksummed and signed with everything else. The assembly step picks the newest tag per minor. No "first tag of the next minor" logic is needed. Make release-engineer co-owner of this ticket and list it as depending on "sign-release workflow with cosign keyless and ordering decision".

4. **Section 7, changelog: `git diff` against the last tag makes `docs --check` non-deterministic.**
   - Problem. The renderer adds, per version, the schema files changed since the previous tag. That output changes the moment a new tag lands, so every open PR goes red until it regenerates. It also needs full history, and CI checkouts are shallow. It contradicts the section 5 rule "output is deterministic".
   - Fix. Write that line into `CHANGELOG.md` at release time (a step in the release runbook / cargo-release hook, from the committed schema files). The renderer then only reads committed files. Keep checkouts shallow.

5. **Tickets: the M1 Install page depends on an M2 ticket, and 09 duplicates a job that 06 already owns.**
   - Problem. "Install page ..." exit test needs the "post-release smoke test", but "Post-release smoke test of the published install command" is an M2 docs ticket. 06 already has the M1 ticket "Post-release verify job on four environments and Windows zip" that does exactly this against the real release.
   - Fix. Delete the M2 docs ticket. The Install page depends on my ticket "Post-release verify job on four environments and Windows zip" and on "Serve install.sh at getrdy.io/install". The `install-only` tested blocks run in that job; I will expose the block extraction as a script.

6. **Tickets, scope: 31 M1 tickets and 85 hours is not defensible next to the rest of M1.**
   - Problem. Six weeks at 10 to 15 hours is 60 to 90 hours for the whole product. My release slice is about 45 hours. Docs alone at 85 hours exceeds the budget. 09 itself says M1 minimum is a scaffold, install, first run, a spec reference generator and one page per M1 check family.
   - Fix. Keep about 17 tickets, 48 hours, in M1 and move 11 tickets, 29 hours, to M2 (details in the table below). Two tickets are also owned wrongly: the schema emitter belongs to the `rdy-spec` owner (rust-engineer) and `CheckMeta` belongs with the check registry (check-author or rust-architect). A docs-writer should read them, not define them. That trims docs-writer M1 to roughly 40 hours.

## Should fix

7. **Section 8 rule 2: root shows the newest tag, including alphas.** 06's `install.sh` installs the latest non-prerelease once one exists. Docs for an unreleased alpha would describe flags the default install does not have. Fix: `/` shows the newest stable tag once one exists, and alphas live under `/next/` (before the first stable tag, `/` shows main with the pre-release banner, as 09 already says).

8. **Section 10, Node pinning is not tight enough.**
   - `.node-version` should hold a full version (for example `24.11.0`), not a major. `engines` as `>=major` lets newer Node pass.
   - Corepack is no longer bundled with newer Node releases. Use the `pnpm/action-setup` action pinned to a commit SHA, which reads `packageManager`.
   - Use pnpm 10 or newer, where dependency install scripts are off by default. Keep an explicit `onlyBuiltDependencies` list (esbuild, sharp, workerd). Set `minimumReleaseAge` to about 7 days so a freshly published, possibly hijacked package does not enter the lockfile. This is a security product.
   - Run `setup-node` with `cache: pnpm` only after pnpm is installed.

9. **Section 6, `cargo xtask` and the workspace.** xtask is a workspace member, so `cargo test`, `clippy` and `cargo doc` cover it, which is good. Two traps. (a) dist treats any binary as an app: set `[package.metadata.dist] dist = false` and `publish = false` in xtask, or the release plan lists it. (b) `rdy-cli` needs a library target to expose `command()`. A lib and bin with the same name `rdy` produce a `cargo doc` output collision. Name the lib `rdy_cli` (or set `doc = false` on the bin).

10. **Section 9 and the corrections: Pages cannot route one path of an apex domain.** The correction "a small Pages project ... bound to the `getrdy.io/install` route" will not work, because the apex is already a Pages custom domain for the marketing site. A path route needs a Worker route (or the marketing build copying the script). I am changing 06 to a Worker route and listing it in the ADR. 09's correction and ADR text should say the same.

11. **ADR 3 against 06: the test knob.** 09 wants no `RDY_BASE_URL`-style variable in a `curl | sh` script. 06 had one. I accept 09's position: test with a stub `curl` on `PATH` and a local file server. I am removing `RDY_BASE_URL` from 06. ADR 3 can be closed as decided.

## Verdict

**Request changes.** Six must-fix items: the deploy token exposure, the CI integration with `ci-ok`, the `release.yml` hand edit and signing order, the non-deterministic changelog render, the M1-to-M2 dependency and duplicate smoke test, and the M1 scope. The structure of 09 is sound (xtask-generated references, Node kept out of the Rust jobs, versions from release assets). Most fixes are edits to the plan, not a redesign.
